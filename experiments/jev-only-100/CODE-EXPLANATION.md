# 현재 E5→JEV 개선판의 코드상 제한

이는 로컬에서 평가한 개선판(원본 커밋32e4ef7)이다. 운영 API 배포 여부를 뜻하지 않는다. 원본 스냅샷은 baseline-source/에 있다.

## 1. 보완 검색: 원문 E5 Top-80의 누락 가능성 줄이기

1. 원문 그대로 E5 검색80개를 받는다(run.py59행).
2. 고정된6개 문자열 치환으로 표현을 정규화한다. 자가용→자동차, 처분→판매, 자가→주택, 사장→사업자, 장사→사업, 창업→사업 시작. 원문과 달라진 경우에만 E5검색40개를 추가로 받는다(run.py61행, retrieval.py4~7행).
3. 정규화한 입력의 단어·연속3글자 조각으로 BM25 방식의 어휘 검색을 한다. 대상은 실제 메뉴명·설명·선택 조건·별칭이다. 메뉴명은3번 반복해 가중한다. 양수 점수의 상위20개까지만 반환한다(retrieval.py9~31행). 정규화E5와 어휘검색은 병렬 호출이 아니라 현재 코드에서 순서대로 처리한다.
4. 원문80개를 우선 보존하고, 정규화E51위→어휘1위→정규화E52위→어휘2위 순으로 교차 추가한다. 동일ID는 건너뛰며 전체100개까지만 자른다. 따라서 추가 후보는 최대20개다(retrieval.py33~38행).

이 보완은 LLM이 새로운 메뉴를 생성하거나 정답을 추가하는 작업이 아니다. 이미 존재하는585개 중 다른 방식으로 재검색한다. 6개 치환은 단순 문자열 규칙이며 문맥·형태소를 완전히 이해하지 않는다. 예를 들어 ‘자가’가 다른 단어 안에 있어도 치환될 수 있다. 광범위한 동의어 인식으로 과장하면 안 된다.

오사카 실제 S01_03에서 원문80개 외에 어휘검색에서 ‘최근 본 상품’1개가 추가돼81개였다. 그 보완 메뉴는 최종 선택되지 않았다. 이 사례는 최종3개 모두 원문80개에 이미 있었다. 따라서 이 예시만으로 보완검색의 성능 기여를 주장할 수 없다.

## 2. 중복 제거: 같은 메뉴 ID를 한 번만 남김

`list(dict.fromkeys(original))`로 원문 내부의 동일ID를 제거한다. 보완 후보도 `not in result and not in supplement`로 검사한다. ID가 같아야 제거하므로 ‘환전신청’과 ‘환전조회/관리’처럼 서로 다른ID의 유사 기능은 여기서 제거하지 않는다. 이름이 같은 서로 다른ID도 자동 병합하지 않는다.

## 3. 중복 완화: 유사 기능을 너무 많이 고르지 않도록 점수 조정

JEV가 메뉴마다 판단한 Noul 적합도가0.30이상인 후보만 남기고 최대10개를 순서대로 고른다. 각 단계 점수는 다음과 같다(set_selection.py5~12행).

`0.7 × JEV 적합도 − 0.3 × 이미 선택한 메뉴들과의 최대 E5 코사인 유사도`

아직 선택한 메뉴가 없으면 유사도 페널티는0이다. 한 개 고른 다음부터 이미 고른 메뉴와 너무 비슷한 후보의 점수가 낮아진다. 고른ID는remaining에서 제거하므로 다시 선택하지 않는다.

0.7은 신뢰도 하한이 아니라 가중치다. 유사도0.9이상이면 무조건삭제 같은 하드 임계값은 없다. 따라서 유사 메뉴가 함께 남을 수 있다. MMR은 점수 완화이고 완전한 업무 중복 제거가 아니다. 기능별 최대1개 같은 코드 제약도 없다.

예: 이미 고른 메뉴와 A의 유사도가.95이고 적합도.85라면 .7×.85−.3×.95=.31이다. B의 유사도가.30이고 적합도.72라면 .7×.72−.3×.30=.414다. 따라서 이 단계에서는 적합도가 더 낮더라도 보완적인 B가 먼저 선택될 수 있다. 이 숫자 예시는 수식 설명용이며 실제 실행 결과가 아니다.

## 4. 120개 조합: 코드가 모든3개 묶음을 열거

`itertools.combinations(pool, min(3, len(pool)))`를 사용한다(set_selection.py20~26행). 후보10개라면10×9×8/(3×2×1)=120개다. A·B·C와 B·A·C는 같은 조합이므로 한 번만 나오고, 한 조합 안에 같은 메뉴가 두 번 나오지 않는다.

각 조합에set_1~set_120이라는 키를 붙이고 실제 메뉴명3개를 Choice 설명에 넣는다. ‘적절한 후보가 없음’none과 ‘목적 확인 필요’unsure를 더해 총122개 선택지가 된다. `assert len(criteria)<=255`로 선택지 수를 제한한다. JEV는120번호출되는 게 아니라 이122개 선택지를 포함한 **한 번의 Choice 호출**로 조합 하나를 고른다.

후보9개면84조합,8개면56조합이다. 후보1~2개면 그 후보 수만큼 묶은1조합이다. 후보0개면최종Choice를 호출하지 않는다. 후보가3개이상일 때1개·2개짜리조합은 만들지 않으므로 현재 코드는 자유로운 추천 개수 선택이 아니다. 지시문에 ‘더 작은 조합’이 있어도 해당 선택지가 없으면 고를 수 없다.

최종 지시문은 비슷한 조회만 모으지 않고 조회·상담·보험·실행 등 보완적 역할을 보도록 요청한다. 메뉴 역할은 이름·설명의 정규식으로 붙이는 일반 태그이며 상황별 고정ID 조합이 아니다. 역할별 수량 제한이 강제되는 것은 아니다. 반환된 Choice가 실제 mapping에 있어야 하고confidence는0~1 유한수여야 한다. 최종 confidence의 최소통과값은 없다(set_selection.py31~34행).

## 5. JEV 단독 비교에서 바뀐 부분

전체585개를80×7+25로 나눠 모든 메뉴를JEV가평가한다. 같은ID가 서로 다른청크에 중복되지 않음을 검증한다. 최대4청크동시, 전체후보별Noul을합쳐0.30이상상위10개를선정한다. 동점은카탈로그순서다. E5벡터가필요한MMR은사용하지않는다. 그다음은위와같은120조합Choice한번이다. 그래서질문당최대8+1=9회,100문항정상최대900회다.

청킹 크기는서비스의 ‘80개질문제한’이아니라이실험이정한값이다. TypeSafe 공식문서상기본64k요청·32k질문당컨텍스트안에들도록묶는취지다. 질문개수자체의별도한도는없다고명시돼있다. API초과시자동으로청크크기를바꾸며재실험하지않고오류로보존·중단한다. 한도429만호출당최대2회재시도한다. 로그에키는출력하지않고원문질문·실제메뉴정보만전송하며정답표는전송하지않는다.
