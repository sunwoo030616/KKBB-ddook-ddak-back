# 복수 메뉴 v2 개발 확인·회귀·추가 검증

v1의 54개 업무 분류와 독립 질문 사이의 순위 슬롯 의존성을 제거한다. 작은 처리 경로 분류는 지원 업무를 제한하지 않는다. 단일 요청은 변경하지 않은 SemanticMenuSelectionService를 재사용한다. 명시적 복수 요청은 보수적으로 분해한 실제 원문별 독립 Choice로 판단한다. 해외여행 기본 묶음은 코드 정책으로 검색하고 제외·완료는 skip으로 처리한다. 분해되지 않는 복수 요청은 E5 후보별 독립 Noul로 필요 여부를 판단한다.

초기 후보는 복수 명시 요청별 20개, 여행 업무별 12개이며 unresolved인 업무만 Top-40으로 한 차례 확장한다. 원문 분해가 불확실한 후보별 필터는 Top-40에서 Noul>=0.7을 사용한다. Noul 확률과 Choice confidence(0.6)를 같은 값으로 취급하지 않는다. 결과 확인 후 평가셋에 맞춰 임계값을 조정하지 않는다. 요청당 실제 외부 호출은 최대 3회이며 기존 단일 선택 경로 자체는 유지한다.

## 데이터 및 순서

1. development-12.json: 이미 실패를 확인한 기존 사례 12개. 개발 확인용이며 성능 주장에 합치지 않는다. 최대 두 차례의 개발 실행을 허용하고 모든 실제 응답을 보존한다.
2. regression-300.json: 이전 평가와 동일한 질문·정답·순서 300개. 개선 전후 대응 회귀 지표를 비교한다. 이전 결과를 보고 구조를 수정했으므로 독립 일반화 성능은 아니다. GPT 이전 결과와 시간/정확도의 동시 대응 비교라고 주장하지 않는다.
3. fresh-100.json: 새 표현의 합성 100개(단일 30·복수 30·상황 30·무관/모호 10). 개발 확인 전에 질문·라벨을 고정하고 변경하지 않는다. 여기서는 JEV v2와 GPT를 질문별 교대 순서로 각 1회 실행한다. 같은 메뉴·상황 의도는 재사용하므로 독립 의도 100개나 전문가 검수 세트가 아니다.

모델: JEV jev-1.14.0, GPT gpt-4o-mini-2024-07-18. GPT는 E5 없이 전체 585개 메뉴와 동일 v2 제품 정책을 받아 최대 3개 메뉴를 선택한다. 구체적인 단일 요청은 하나만 반환하고 복수 요청은 모두 반환하도록 양쪽 정책에 명시한다. GPT는 temperature=0, strict JSON Schema, max_tokens=500이다. 프롬프트/정책이 개선된 이번 GPT 결과를 이전 실행의 GPT 점수와 직접 개선율로 비교하지 않는다.

## 판정과 측정

오류는 분모에 남긴다. 전체는 상태+메뉴 집합 일치를 기본 지표로 쓰고, 메뉴 집합만의 일치도 따로 저장한다. 정답 메뉴가 있는 90개에서만 Macro P/R/F1을 계산한다. 무관/모호 10개는 no_match/needs_clarification 상태와 빈 메뉴를 모두 만족해야 정답이다. 미제공 토큰은 null, 실제 API usage는 모든 단계 합산이다. 캐시는 입력 토큰의 부분집합이며 API간 token 정의가 같다고 가정하지 않는다.

시간은 로컬 HTTP 요청 시작부터 최종 응답까지로 JEV 라우팅·E5 질의·선택/후보 확대와 proxy 오버헤드를 포함한다. 컴파일·서버/모델 기동·메뉴 임베딩 준비와 명시적 rate-limit 대기는 제외한다. 실패·조기종료를 포함한 전체 평균과 양쪽 성공한 동일 문항의 조건부 평균을 구분한다.

평가 중 외부 장애에 대한 재시도는 하지 않는다. 개발 확인은 최대 24개 요청, 회귀 300개 요청, 추가 검증 100개 요청으로 JEV 최대 1,272회, 새 100개에 대한 GPT 100회가 상한이다. 같은 API가 반환한 usage를 기록하고 개발 비용을 평가 사용량과 합치지 않는다. 이 변경 범위는 사용자의 외부 실행 승인을 받은 후 수행한다. 키는 기존 환경/IntelliJ 설정에서 메모리로 읽고 기록하지 않는다. 임시 복사본의 JEV 두 client endpoint와 대응 mock URL만 usage proxy로 바꾸며 원본 판단 코드는 바꾸지 않는다.

새 라벨은 API 실행 전에 cases/label 문서와 해시로 보관한다. 개발 결과에 따른 코드 수정은 개발 로그·커밋으로 보존하고, 본 평가의 소스와 설정은 개발 종료 후 별도 해시로 고정한다. 평가 결과를 본 뒤 같은 실행의 정답·정책·입력은 바꾸지 않는다.

## 개발 단계의 추가 구조 수정

첫 완전한 개발 실행(12건)에서 9건 일치했고, 유형을 단일 Choice로 나누는 판정이 일부 요청을 잘못 막거나 검색 원문이 완료 이력에 묻히는 문제가 남았다. 유형 판정도 4개의 독립 Noul(여행 기본 묶음/명시적 복수/무관/정보 부족)로 교체했다. 여행·복수 확률은 0.7, 명백한 무관·정보 부족의 조기 종료는 0.9를 사용하며 평가 결과로 맞춘 값이 아니다. 단일 Choice confidence=0.6은 기존 메뉴 선택 경로에만 적용한다.

분해되지 않은 복수 요청의 검색에는 원문 및 '이번에는' 뒤의 현재 요청, 접속 명사구를 최대 4개 질의로 추가해 라운드로빈으로 최대 60개 실제 후보를 모은다. 질의 분해는 검색 확장만 하며 최종 판단은 완료·제외가 포함된 원문 전체를 본다. 실제 원문 요청이 분리된 경우에는 여전히 요청별 독립 Choice를 사용한다. 54개 업무 목록은 사용하지 않는다.

첫 저장 실패의 1건, 첫 완전 개발 확인 12건, 보완 후 10건으로 개발 요청은 합계 23건이다. 실패를 본 세 문항과 나머지 일곱 문항의 재확인을 개발용으로 기록하며 본 평가 점수에 합치지 않는다. 새 100문항 질문·정답 해시는 변경하지 않았다.

보완 개발 10건에서는 9건 일치했다. 남은 한 사례는 여행 기본 묶음을 이미 완료하고 로밍·여권을 요청했는데 여행 분기로 들어가 기본 묶음만 제외하고 끝난 경우다. 기본 묶음이 전부 skip이고 호출 예산이 남았으면 원문의 다른 요청을 후보별 판정으로 검색하는 제한적 fallback을 추가했다. 요청당 최대 3회 호출은 유지한다. 이 알려진 사례 1건을 최종 개발 확인하여 개발 요청 합계는 저장 실패 포함 24건을 넘기지 않는다. 평가용 새 100개 라벨과 정책 기본 묶음·임계값은 바꾸지 않았다.

최종 개발 확인 1건은 두 메뉴 모두 반환했다. 이후 본 평가 전에 proxy 로그에 JEV 원본 answers(선택·확률) 저장만 추가했다. 추론 코드·프롬프트·임계값은 바꾸지 않았다. 개발 결과는 source commit과 응답/검증 로그로 보존한다.
