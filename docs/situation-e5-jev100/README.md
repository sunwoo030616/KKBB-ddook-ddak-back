# LLM 없는 E5→JEV 100문항 실제 검증

사용자 요청에 따라 같은 승인된 상황형 100문항에서 원문 E5 Top80 → JEV 메뉴별 Noul → 최대3개 선택을 실제 실행했다. GPT/OpenAI 호출은 0회다. 상황별 고정 추천표는 넣지 않았다.

| 지표 | E5→JEV만 | LLM→E5→JEV | GPT-4.1 단독 |
|---|---:|---:|---:|
| 부분 적중률 | 84% | 83% | 89% |
| 허용 메뉴 비율 | 54.95% | 63.11% | 51.36% |
| 필수 업무 Recall | 61.67% | 54.00% | 52.83% |
| 문항당 추천 메뉴 | 2.73 | 2.06 | 2.94 |
| 평균 / P95 HTTP ms | 442.68 / 574.11 | 1957.30 / 2762.34 | 1273.41 / 1708.20 |
| 문항당 입력 / 출력 토큰 | 19,838.77 / 1,764.00 | 23,513.50 / 810.46 | 25,855.92 / 26.65 |
| 100문항 API 비용 추정 | $0.0833 | $1.0196 | $1.4854 |

## 실패 지점

부분 미적중16건 중 후보 누락 3건, 후보가 있지만3위 밖 12건, 허용 후보 전부0.7미만 1건이다.

은퇴 상황 9건에서는 나의 은퇴자산 현황·나의 연금자산·은퇴준비를 위한 KB골든라이프 같은 메뉴를 추천했지만 현재 허용 정답 목록 밖이라 실패다. 기능상 타당한 대체인지 사람 검수가 필요하다. 이 9건을 자동으로 정답 처리하거나 기존 점수를 덮어쓰지 않았다. 양쪽 모델을 같은 수정 기준으로 재검산하고 새 상황에서 검증해야 하며, 라벨 변경은 모델 개선이 아니다.

## 오프라인 다양성 재정렬 확인

같은 실제 JEV 응답과 실제 E5 벡터로 고정 MMR(lambda0.7) 재정렬을 한 번 확인했다. 부분 적중85/100으로1건 증가했지만 단독 LLM89를 넘지 못했다. 이는 새API 실행이나 새종단간 시간 측정이 아닌 노출된 동일 데이터의 개발 분석이다. 매개변수 탐색으로 좋은 수치만 고르지 않았다.

## 다음 개선 후보

- 후보별 독립 확률 상위3개 대신, 최종 후보10개에서1~3개로 구성된 실제 메뉴 조합(175개)을 만들어 JEV가 조합 단위로 선택하는 실험. 한 목적의 비슷한 메뉴가 자리를 독점하는지 확인한다. 개선을 보장하지 않으며 아직 실행하지 않았다.
- 검색 누락3건은 별칭·표현 차이를 점검하고 실제 키워드 검색/벡터 검색의 결합을 별도 검증한다. 현재후보포함97%를 최종정확도로 부르지 않는다.
- 모든 신규 정책·임계값 조정은 개발 데이터에서 하고, 새 상황군에서 단독 LLM과 같은 메뉴 예산으로 검증한다. 평가 정답표를 추론 규칙에 넣지 않는다.

## 비교 한계

- 같은100문항이지만 이미 노출된 개발용 비교다. K=80도 로컬 후보 포함률을 본 뒤 선택했다. 독립 검증이나 실제 사용자 정확도라고 표현하지 않는다. 10상황군×10표현이다.
- 순수 경로는 최대3개, 이전두조건은 최대8개였다. 기존 단독 LLM 응답의 첫3개만 잘랐을 때 부분적중78%지만, 이는 단독 LLM에 처음부터3개만 요구한 공정한 재실험은 아니다. 이수치를 우월성 증명으로 쓰지 않는다.
- 이번실험은 로컬Python E5/직접JEV, 이전혼합은 실제Java API/proxy를 거쳤고 실행시각도다르다. 기동은제외했지만 네트워크·구현 오버헤드가 달라 생산환경 SLA나 완벽한 인과비교가 아니다.
- 비용은 관측JEV입력×$0.042/M, 출력무료라는 [TypeSafe 공개 단가](https://help.typesafe.ai/articles/5187202169-how-much-does-jev-cost)에 따른 추정이다. 로컬E5 CPU/운영비·세금은제외했고 청구서가 아니다. 다른제공자의 토큰수를 같은가격단위로 비교하지않는다.
- 실제 선택코드·0.7기준·최대3개는 API판단실행 전에 고정했다. 정답과 허용대체는 이전승인버전그대로다. 기본프로젝트 API를 이경로로 배포하거나 GitHub에 게시하지 않았다.
