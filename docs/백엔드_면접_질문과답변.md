# 깨비뚝딱 확장: 백엔드 면접 질문과 답변

수상 당시의 채팅 기반 금융 위젯 구성과 이후 개인 확장을 구분한다. 현재 측정값과 설계는 [최신 플랫폼 결과](문헌검색_병목분석_플랫폼개선.md), 재현 명령은 [MCP·파이프라인 실행](MCP_Skill_수집파이프라인_실행.md)에 있다.

## 왜 서비스에 문헌 탐색을 붙였나요?

고객은 채팅으로 금융 기능을 요청하고 서비스는 위젯 화면을 구성한다. 문헌 탐색은 이 제품을 개발하고 검수하는 사람의 내부 도구다. 금융 안내와 RAG·문서 추론·서빙 연구를 출처 버전과 함께 관리하고, 모델이 제안한 구절을 검토할 수 있게 확장했다. 논문의 초록에서 찾은 내용을 고객의 거래나 금융 자격 판정에 바로 사용하지 않는다.

3번 직무에는 공식 문헌 수집, 원문 정제, 질의 생성, 근거 연결, 검토 데이터 관리가 연결된다. 백엔드 직무에는 이 작업의 중복 방지와 복구, 데이터 버전, 검토 충돌 처리가 연결된다.

## 모델이 JSON을 잘 만들면 충분하지 않나요?

JSON 형식, 요구사항 보존, 검색 회수, 근거의 의미 적절성은 서로 다른 문제다. 구조화 디코딩 뒤에도 서버에서 스키마를 검증하고, 검색 결과 중 선택 가능한 근거만 받는다. 출처 ID와 원문 인용 위치가 유효해도 질문에 대한 충분한 근거라는 뜻은 아니다. 내부 진단에서도 문헌 선택 실패가 남아 있어 모델 출력을 검토 후보로 취급한다.

## 왜 작은 생성 모델로 모두 교체하지 않았나요?

같은 개발 문항에서 1.7B와 4B를 별도 프로세스로 비교했다. 작은 생성 모델의 속도만 보지 않고 주제 손실과 없는 근거의 누락 표시도 확인했다. 이후 기본 문헌 경로는 작은 다국어·영어 검색 모델로 원문을 읽고, 불확실한 후보의 지원 여부만 4B 생성 모델에 묻도록 바꿨다. 작은 전용 번역 모델도 비교했으나 기술 용어가 바뀌어 기본에 채택하지 않았다. 모델 크기보다 단계별 요구 조건으로 역할을 정했다.

## 후보를 줄이면 어떤 문제가 생기나요?

임베딩으로 후보를 줄인 뒤 재평가하면 비싼 점수 계산 수를 제한할 수 있다. 하지만 첫 후보 집합에서 목표 문헌이 빠지면 뒤의 Cross-Encoder는 복구할 수 없다. 그래서 후보 포함 여부와 최종 Hit@1·Hit@3를 따로 기록했다. 현재 수십 편에서 정확한 코사인 유사도를 전수 계산하며, ANN이나 대규모 검색 성능을 구현한 것으로 설명하지 않는다.

## 중복 작업을 어떻게 막았나요?

문서 ID, 원문 해시, 모델 식별자, 프롬프트 버전으로 작업 키를 만든다. 같은 입력은 다시 등록하지 않고 현재 상태를 재사용한다. 원문이나 프롬프트가 달라지면 별도 작업이 된다. 무변경 갱신에서는 모델 적재와 추론 자체를 건너뛰는 것을 실제 실행으로 확인했다.

## 작업자가 죽거나 오래 걸리면요?

SQLite 쓰기 트랜잭션에서 임대 토큰과 만료 시각을 부여한 뒤, 트랜잭션 밖에서 추론한다. 저장할 때 현재 토큰과 만료 시각을 다시 확인한다. 만료 후 다른 작업자가 가져간 작업에 예전 결과가 도착해도 저장하지 않는다. 추론이 중복 실행될 가능성까지 제거한 exactly-once가 아니라, 늦은 작업자의 결과가 현재 상태를 덮어쓰는 것을 막는 설계다.

단일 SQLite의 동시 쓰기는 직렬화된다. 여러 서버를 운영해야 한다면 작업 저장소, 임대 갱신, 큐 전달과 장애 시나리오를 다시 설계해야 하며 이번 구현에서 그 규모까지 검증하지 않았다.

## 왜 추론 중 DB 트랜잭션을 유지하지 않나요?

추론은 수십 초 걸릴 수 있다. 그동안 쓰기 잠금을 잡으면 다른 문서의 작업 취득이나 검토도 막힌다. 짧은 트랜잭션으로 작업을 가져오고, 긴 외부 계산을 끝낸 뒤 별도 트랜잭션에서 소유권과 원문 버전을 검증해 저장한다. 사이에 원문이 교체되었다면 결과를 버리는 것이 이 분리의 비용이다.

## 검토 충돌과 승인 취소는 어떻게 처리하나요?

검토에 예상 리비전을 요구한다. 다른 검토자가 먼저 변경한 상태를 오래된 화면으로 덮어쓰면 충돌로 거부한다. 발행은 승인 카드 목록과 검토 리비전의 스냅샷을 만들고 활성 포인터를 한 트랜잭션에서 바꾼다. 검색 중 승인이 취소되거나 원문이 바뀌어도 마지막 버전 검사를 통과하지 못하면 결과를 비운다. 롤백 역시 현재 유효한 승인과 원문일 때만 허용한다.

## 결과 캐시와 KV 캐시는 뭐가 다른가요?

결과 캐시는 시스템 지시문·입력·스키마·토큰 예산·모델 식별자가 같은 요청의 생성 결과를 재사용한다. 시스템 KV 캐시는 시스템 지시문의 사전 계산을 재사용해 뒤의 사용자 입력은 다시 생성한다. 후자는 전체 프롬프트와 prefix+suffix의 토큰열이 정확히 일치할 때만 적용하며 저장한 KV를 복제한다. 사용자 입력이 저장된 시스템 KV를 변경하게 두지 않는다.

캐시는 프로세스 내부에 제한된 개수와 크기로 보관한다. 결과 캐시가 적중해도 실제 계산 도구와 기준일별 금융 근거는 서버에서 다시 처리한다. 서로 다른 사용자 코드의 생성 검사와 서로 다른 금융 기준일의 화면 API 회귀를 구분해 검증했다.

## 9번의 서빙 경험으로 어디까지 말할 수 있나요?

단일 Mac에서 CPU 검색 모델과 GPU 생성 모델의 단계별 시간을 기록하고, 입력 후보 예산·구조화 디코더 재사용·시스템 KV·메모리 정책을 비교했다고 설명할 수 있다. 두 생성 모델을 동시에 적재해 지연이 나빠진 실험도 보존했다. 분산 학습, 통신 최적화, 이종 가속기 클러스터 운영을 했다고 말하지 않는다. 그 부분은 지원 후 배우고 싶은 영역이다.

## 금융권 백엔드에 무엇을 연결할 수 있나요?

모델의 화면 계획과 실제 금융 데이터를 분리한 점, 기준일에 맞는 근거를 다시 조회한 점, 멱등 작업 키와 상태 전이, 낙관적 리비전, 짧은 트랜잭션, 장애 후 복구를 구체적인 코드와 함께 설명한다. 금융 거래 원장이나 은행 운영 시스템을 구현한 경험으로 확대하지 않는다. 실제 사용자가 있었던 기존 프로젝트 경험과 이번 로컬 실험의 수치는 각각의 근거로 설명한다.

## MCP와 Skill은 어떻게 다른가요?

MCP 서버는 검색·현재 인용·상태·통계 기능을 타입이 있는 도구로 제공한다. Skill은 그 도구를 어떤 상황에 사용하고 무엇을 검토할지 안내한다. 실제 권한 경계는 서버에 승인·삭제 도구를 제공하지 않는 방식과 DB·인용 검증으로 유지한다. Skill 지침만으로 보안을 강제한다고 설명하지 않는다.

## 배치 수집의 재개와 AI 작업의 재실행은 같은가요?

JSONL 수집은 문서·버전·색인·커서를 같은 DB 트랜잭션에 저장한다. 커밋 전에 실패하면 모두 롤백되고 마지막 커밋 위치에서 이어간다. AI 후보 생성은 긴 추론을 쓰기 트랜잭션 밖에서 처리하므로 장애 시 추론 자체가 반복될 수 있다. 대신 임대 토큰으로 오래된 결과가 저장되는 것을 막는다. 서로 다른 경계의 보장 범위를 구분해 설명한다.

## 본문·복수 인용과 외부 평가를 왜 추가했나?

초록에는 알고리즘의 검증 절차가 없거나, 긴 저자 주장 문장이 잘리면서 명시 조건이 빠질 수 있었다. 공식 PDF 일부 페이지를 추출하고, 문서 버전과 페이지별 위치를 보존한 뒤 한 요청 절에 최대 두 인용을 연결했다. 서로 다른 인용을 합쳐 원문처럼 제시하지 않고 각 구간을 다시 확인한다. PDF 바이트 위치와 정규화된 추출 텍스트 위치는 구분한다.

## 개발 문항을 잘 맞히면 충분한가?

기존 24문항은 개선 과정에서 이미 관찰했다. 그래서 구현 전에 별도 12문항을 커밋하고, 외부 연구자가 정답 문헌과 근거 문장을 표시한 SciFact 표본도 사용했다. 내부 핵심 회귀는 24/24였지만, 사전 고정 문항은 10/12, SciFact 표본은 문헌 9/10·정답 근거 문장 하나 이상 포함 6/10이었다. 원문 위치 일치와 의미적 지지는 다르다는 점을 결과로 확인했다. 전체 SciFact나 금융권 운영 성능으로 해석하지 않는다.

## 평가에서 실패를 찾으면 어떻게 처리했나?

사전 고정 문항 중 승인·게시 연속 명령의 라우팅 오류는 수정 전 결과를 커밋한 뒤 별도 기능 수정으로 처리했다. 최초 점수를 올려 쓰지 않고, 수정 후 실제 API가 모델 호출 없이 범위 밖으로 응답하는지 확인했다. RAG의 새 표현을 잘못 찾은 사례는 숨기지 않고 다음 검색 개선의 기준으로 남겼다. 이제 그 문항은 관찰한 회귀 사례이므로 다음 개선을 검증할 새 평가 자료가 필요하다.

## 금융권 백엔드 지원에서 어떻게 설명하나?

고객의 채팅으로 금융 위젯 화면을 만드는 제품에서 모델의 제안과 서버의 실행 책임을 분리했다. 출처 버전, 인용 구간, 재조회, 작업 상태와 DB 트랜잭션은 서버가 관리한다. 문헌 검색은 이 구조를 연구·검수하는 내부 도구이며 기술 논문을 실제 금융 거래·자격 판단의 근거로 쓰는 기능은 아니다. 검증 가능한 부분과 의미 판단이 남는 부분을 구분해 설계·측정한 경험으로 설명한다.
