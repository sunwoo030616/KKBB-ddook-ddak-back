# 복합 금융 요청을 위한 신경망 위젯 검색

2026-11-03. 기존 채팅 → 위젯 구성 서비스의 후보 검색을 확장한다.

## 발견한 문제

12문항 개발 진단에서 “예금을 깨는 것과 담보로 돈을 빌리는 비용을 비교하고, 대출을 받으면 매달 얼마씩 갚는지도 보고 싶다”는 요청의 전체 문장 점수는 자금 비교 0.4460, 월 상환표 0.000389였다. 상대 점수 컷오프 때문에 상환표가 후보에서 빠졌다. JSON 제약은 후보에 없는 기능을 복원할 수 없으며, 뒤에 LLM 검토를 더 붙여도 초기 설계가 실패하면 도달하지 못했다.

또한 주식 자동매수처럼 미지원 요청도 상대 순위의 상위 후보를 강제로 하나 이상 골랐다. 낮은 관련도를 정답 확률로 오해하면 엉뚱한 금융 화면을 만든다.

위 수치는 특정 개발 질문의 BGE 출력이며 모델 전체의 성능 추정치가 아니다.

## 추가한 경로

`ComposeRequest.retrieval_mode="multi"`로 사용한다.

1. 원문을 항상 유지하고 문장·쉼표·한국어 연결 표현에서 보조 절을 만든다. 최대 4개 검색 관점으로 제한한다.
2. BAAI/bge-reranker-v2-m3가 각 관점 × 활성 업무 위젯의 의미 관련도를 실제 추론한다. 위젯 이름을 키워드 사전으로 매핑하지 않는다.
3. 관점별 최고 점수로 상대 정규화한다. 보조 절의 배경 최저 점수는 빼서 평평한 잡음 점수가 모두 후보를 승격시키지 않도록 한다. 원문 관점은 유지한다.
4. 관점별 값을 합쳐 최대 8개 후보를 고르고, 기존 화면의 유효한 위젯도 보존한다. 상충 액션은 원문 관련도도 사용해 결정한다.
5. 모든 관점의 원 점수 최댓값이 0.001 미만이면 후보를 강제 선택하지 않는다. 확인 안내로 반환하고 LLM 생성을 생략한다.
6. 최종 위젯 선택과 제외 조건 해석은 기존 Qwen3-4B 구조화 설계가 수행한다. 입력 의존관계·상태 보존·계산은 기존 서버가 처리한다.

문장을 나누는 부분은 규칙 기반 전처리다. 의미 점수는 실제 cross-encoder가 계산한다. 이를 LLM이 질문을 분해했다고 표현하지 않는다. 0.001은 개발용 보수적 휴리스틱이며 독립 자료로 보정한 신뢰도나 확률 임계값이 아니다. 새로운 표현에서 잘못된 거부가 생길 수 있다.

## 평가

```bash
.venv/bin/python -m pytest tests_rag/test_component_queries.py -q
.venv/bin/python -m rag_backend.evaluate_component_queries
```

`reports/component-query-v1.json`은 기존 single-query/off 결과와 multi-query/off 결과를 비교한다. 생성 모델·프롬프트·출력 스키마·골드 목록은 유지하지만, 후보 검색 관점·합집합·낮은 관련도 중단과 함께 CPU float32 → Apple GPU float16 실행도 변경했다. 하나의 요소만 바꾼 인과 실험이 아닌 시스템 개발 비교다. 따라서 효과를 문장 분할 하나만의 인과 효과로 해석하지 않는다.

정답 목록은 평가기에만 전달한다. 정확 위젯 집합, 후보 재현율, 개선/악화 사례와 지연을 보존한다. 앞선 실패를 보고 고친 개발 평가라서 이 문항을 미사용 검증셋으로 부르지 않는다. 후속 요청은 동일 구조의 세션 fixture이며 실제 전체 대화 생성과 구분한다.

## 포트폴리오에서 설명할 내용

- “LLM 모델을 더 호출했다”보다 “어느 단계가 실패하는지 분리 측정하고, 복합 의도의 후보 누락과 미지원 요청의 강제 선택을 줄였다”가 핵심이다.
- 검색 후보가 좁으면 constrained decoding이 오히려 필요한 기능 선택을 막을 수 있다. 후보 재현율과 최종 화면 정확도를 따로 측정한다.
- 문법적으로 유효한 UI와 사용자 목적에 맞는 UI를 구분한다.
- 검토 모델의 추가 지연과 잘못된 피드백도 측정해 기본 경로 채택 여부를 결정한다.


## 로컬 추론 실행 보강

검색 모델의 기본 실행 장치는 `auto`다. Apple MPS가 있으면 float16으로, 없으면 CPU float32로 실행한다. `RERANKER_DEVICE=cpu` 또는 `mps`로 명시할 수 있다. `/health`의 `reranker_execution`으로 실제 설정을 확인한다. NaN/무한대 점수는 위젯 후보 선택 전에 거부한다.

[Sentence Transformers 공식 문서](https://www.sbert.net/docs/cross_encoder/usage/efficiency.html)의 MPS와 float16 지원을 사용했다. CPU 실험에서 긴 요청 하나가 207초 걸려 프론트의 180초 제한을 넘었고, 이 실행은 `reports/component-query-cpu-partial.json`에 중단 사유와 함께 보존했다.

MPS float16으로 기존 CPU 점수를 다시 계산한 `reports/reranker-mps-parity.json`에서는 비교 가능한 11개 질문의 최상위 위젯이 모두 같았다. 최대 점수 차이와 각 조회 시간을 남겼다. 이는 모든 순위·임계값·미래 질문의 동등성을 보장하지 않는다. 워밍업 뒤 단일 문장 조회는 대체로 약 0.6~1.3초였지만, 모델 로딩·전체 생성·엄밀한 동시 서버 처리량과는 다른 측정이다.

완료 결과는 [시스템 비교 표](../reports/component-query-results.md)에 있다. 연결 오류를 제외한 비교에서 6/11 → 10/11이며 국내여행의 부정 요청 1건이 남았다. 이 실패를 숨기거나 개발 자료를 독립 검증셋으로 표현하지 않는다.
