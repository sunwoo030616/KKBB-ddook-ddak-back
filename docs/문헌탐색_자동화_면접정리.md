# 문헌 탐색·지식베이스 자동화와 로컬 추론 최적화

이 문서는 32개 문서를 사용한 초기 기록이다. 현재 초록 30편·금융 안내 26개로 확장한 결과는 [무료 모델 개발 결과](무료모델_개발결과_면접정리.md), 새 작업·검토 워크플로는 [지식 큐레이션 운영](지식큐레이션_운영과_면접.md)을 참고한다.

2026-11-04 후속 개발. 기존 채팅 → 금융 화면 구성 경험을 유지하면서, 문헌·금융 안내를 관리하는 내부 지식 처리 도구를 추가했다. 유료 생성 API나 유료 GPU를 사용하지 않는다.

## 1. 무엇이 새로 생겼나

이전에는 Crossref의 제목·저자·DOI 메타데이터를 검색했다. 이번에는 arXiv 공식 API에서 실제 초록 6편을 수집하고, 금융 안내 26개와 함께 32개 문서를 버전 관리한다. 논문 전문 전체를 분석한 것은 아니다.

- 문서 ID, 출처 URL, 원문·메타데이터 해시를 저장한다.
- 같은 내용은 건너뛰고 변경된 문서만 새 버전으로 저장한다.
- 문서가 바뀌면 이전 해시의 근거 후보는 현재 결과에서 제외한다. 버전을 복원하면 해당 버전의 후보를 다시 조회할 수 있다.
- 키워드 검색과 다국어 BGE cross-encoder 검색을 비교한다. 영어 초록을 한국어로도 찾는다.

## 2. AI가 구체적으로 하는 일

서버가 원문을 최대 16단어·180자 이내의 구간으로 나누고, 각각 s0·s1 같은 ID와 정확한 시작·끝 위치를 부여한다. Qwen3-4B는 그중 정보가 있는 구간 ID와 분류·태그를 선택한다.

출력 스키마의 span_id는 실제 존재하는 ID로 제한한다. 모델에게 원문 인용을 다시 쓰게 하지 않고 서버가 선택된 구간을 복사한다. 그 뒤 원문 위치와 문서 해시를 다시 확인한다.

**보장하는 것은 출처 위치의 일치다.** 선택한 구간이 질문에 충분한지, 분류·태그가 올바른지, 논문의 주장이 사실인지는 별도 검토가 필요하다. 그래서 결과 상태는 pending_review이며 금융 화면의 승인된 지식으로 자동 승격하지 않는다.

실제 모델 실행에서 32개 문서 모두 근거 후보가 만들어졌고 출처 위치가 일치했다. 이는 과학적 사실 정확도 100%를 의미하지 않는다.

## 3. 자동화 흐름과 증분 처리

```text
공식 초록 수집 → 문서 해시 비교 → 변경 문서 저장
→ 변경 문서의 AI 근거 구간 선택 → 출처 검증 → 검수 후보 저장
```

```bash
# 기존 스냅샷으로 변경 검사·근거 후보 처리
.venv/bin/python scripts/refresh_knowledge.py

# arXiv 공식 스냅샷을 새로 수집한 뒤 같은 작업 수행
.venv/bin/python scripts/refresh_knowledge.py --refresh

# 검색·캐시 실험까지 한 번에 실행
.venv/bin/python scripts/run_knowledge_lab.py
```

처리 키는 문서 ID·내용 해시·모델 식별값·프롬프트 버전이다. 같은 조합을 재실행하면 이전 결과를 사용한다. 실패도 기록하며 조용히 무한 재시도하지 않는다.

32개 문서를 다시 처리한 실제 실행에서 새 추론은 0회였다. LazyMLXGenerator는 처리할 문서가 없을 때 가중치를 로드하지 않아 모델 로딩도 0회였다. 이미 돌아가는 모델 서버의 응답을 재사용한 결과가 아니다.

## 4. 검색 비교와 남은 실패

초록 6편에 대해 영어·한국어 쌍 12개 질의를 먼저 고정했다. 개발자가 초록을 읽고 만든 작은 진단 자료이고 언어 쌍은 독립 표본이 아니다.

| 방식 | Hit@1 | Hit@3 | MRR@3 |
| --- | ---: | ---: | ---: |
| 단어 겹침 검색 | 6/12 | 6/12 | 0.500 |
| 다국어 신경망 검색 | 11/12 | 12/12 | 0.958 |

한국어와 영어의 단어가 직접 일치하지 않을 때 작은 후보 전체를 신경망으로 재정렬한다. 따라서 이 비교는 같은 후보에서 재정렬만 추가한 실험이 아니라 전체 검색 경로 비교다. 대규모 ANN 성능으로 확대하지 않는다.

한국어의 추론·도구 실행 질의 한 건은 기대한 ReAct가 2위, Adaptive-RAG가 1위였다. 관련 문헌이 상위 후보에 있어도 가장 적절한 문헌을 항상 첫 번째로 선택하지는 못했다. 이 실패를 보고 질의를 수정해 원래 평가 점수를 덮어쓰지 않았다.

## 5. 서빙 최적화: 정확히 같은 입력만 재사용

추가한 것은 **추론 결과 캐시**이며 KV 캐시·prefix 캐시가 아니다. 고정된 모델 인스턴스에서 시스템 지시·사용자 입력 전체·출력 스키마·최대 토큰 수·모델 식별값을 합쳐 해시 키를 만든다.

- 프로세스 메모리에만 보관하고 TTL 300초, 최대 32항목, 직렬화된 결과 2MB 예산을 둔다. Python 객체 전체 메모리 한도라는 뜻은 아니다.
- JSON 스키마를 통과하지 못한 출력과 예외는 저장하지 않는다.
- 같은 입력이 동시에 오면 첫 추론을 기다리고 결과를 공유한다.
- 모델의 선택 결과만 재사용한다. 금융 데이터 조회·계산·화면 revision 갱신·거래 권한 검사는 서버에서 계속 수행한다.

두 입력을 각각 3번 반복한 실제 비교에서 모델 호출은 캐시 off 6회, on 2회였다. 네 개의 동일 입력을 동시에 보낸 실험에서도 모델 추론은 1회, 출력은 모두 같았다. 반복이 없는 새 질문의 생성 시간을 줄였다는 뜻은 아니다.

캐시 hit의 매우 짧은 시간과 최초 생성 시간을 섞어 전체 서비스가 수천 배 빨라졌다고 표현하지 않는다. 운영 트래픽의 hit rate도 아직 측정하지 않았다.

## 6. 깨비뚝딱과 연결되는 이유

금융 화면에 표시할 설명은 출처·시점·버전을 관리해야 한다. 이 도구는 설명 자료를 수집하고 변경된 부분의 검수 후보를 만드는 내부 처리 계층이다. 고객 화면에는 기존 검수 corpus를 계속 사용하고, AI가 붙인 분류·태그를 자동으로 승인하지 않는다.

읽기 API는 `/knowledge/status`, `/knowledge/search`다. 초록과 금융 안내는 kind로 구분한다. 주 서비스의 입력·계산·근거 표시는 기존 React → Spring → Python 경로를 유지한다.

## 7. 면접에서 1분 설명

> 금융 상황에 맞는 화면을 구성하는 서비스를 확장하면서, 화면 근거를 관리하는 문헌·지식 처리 도구를 개발했습니다. 공식 논문 초록과 금융 안내를 내용 해시로 버전 관리하고, 로컬 LLM이 원문 구간 ID를 선택하도록 구조화했습니다. 인용문을 모델이 다시 쓰지 않게 해 출처 위치를 검증했고, 분류 결과는 검수 후보로 저장했습니다. 한국어·영어 검색을 비교하고 오답 사례를 남겼으며, 변경 없는 재실행에서는 추론과 모델 로딩을 생략했습니다. 서빙에서는 동일 입력 캐시와 중복 동시 요청 처리를 검증하되, 새 질문의 추론 속도 개선과 구분했습니다.

## 8. 예상 질문

**왜 모델에게 요약을 바로 쓰게 하지 않았나?** 원문에 없는 문장이 생성될 수 있기 때문이다. 먼저 출처가 명확한 구간을 고르는 문제로 제한했다. 의미 검증이나 요약 품질을 해결했다고 주장하지 않는다.

**왜 새 버전에서 이전 후보를 숨기나?** 같은 문서 ID라도 원문이 달라지면 기존 인용 위치가 틀어질 수 있다. 현재 문서 해시와 일치하는 후보만 조회한다.

**캐시 때문에 과거 금융 정보가 재사용되지 않나?** 전체 HTTP 결과를 저장하지 않는다. 모델 입력이 같아 선택을 재사용해도 실제 근거는 요청의 기준일로 다시 조회한다. 실제 Spring 통합에서도 세션 분리와 과거 기준일 근거 선택을 검사한다.

**9번의 분산 학습까지 해봤나?** 이번 작업은 단일 Apple Silicon의 로컬 추론·메모리 예산·중복 처리 실험이다. 분산 학습과 가속기 간 통신 최적화는 앞으로 배울 영역이다.

**3번과는 무엇이 연결되나?** 문헌 수집·정제, 지식베이스 버전 관리, 신경망 검색, 모델의 근거 선택과 출처 추적, 재현 가능한 오류 분석이다.
