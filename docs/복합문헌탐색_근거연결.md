# 복합 문헌 탐색과 근거 연결

이 문서는 초록 6편을 사용한 초기 실험 기록이다. 현재 확장 경로와 비교 결과는 [무료 모델 개발 결과](무료모델_개발결과_면접정리.md), 작업 복구·검토 절차는 [지식 큐레이션 운영](지식큐레이션_운영과_면접.md)을 참고한다.

2026-11-04. 무료 로컬 Qwen3-4B와 BGE를 사용한 내부 문헌 검수 API다. 논문 초록 6편을 대상으로 한다.

## 동작

사용자 요청 → 최대 3개 정보 과제 → 과제별 검색 → 공통 문서 예산 3개 → 원문 구간 후보 → LLM의 근거 ID 선택 → 출처·현재 버전 재검증 순서로 처리한다.

- 분해한 과제의 request_quote는 원래 요청에 실제 존재해야 한다. 요청에 없는 과제를 추가하면 거부한다.
- 과제별 선택 가능 근거 ID를 출력 스키마로 제한하고, 실제 문서 해시·원문 위치를 서버가 연결한다.
- 근거가 없으면 해당 과제를 missing_task_ids로 표시한다. 생성 답변을 채우지 않는다.
- 추론 중 원문 버전이 바뀌면 stale_snapshot으로 표시하고 인용을 반환하지 않는다.
- 연결은 과제 ID → 문서 해시 → 원문 구간의 추적 구조다. 과학적 사실 검증이나 인과 관계 추론을 수행한 것은 아니다.

## API

POST /knowledge/research, JSON: question과 mode(single 또는 decompose). 기본값은 single이다.

```bash
.venv/bin/python scripts/dev_stack.py
.venv/bin/python scripts/evaluate_evidence_graph.py
.venv/bin/python scripts/summarize_evidence_graph.py
```

## 같은 문서 예산의 실제 비교

개발자가 초록을 읽고 만든 복합·중복 주제·미지원 요청 8개다. 외부 벤치마크나 블라인드 평가가 아니며 초기 실행을 관찰한 뒤 입력·컴파일 경로를 보완한 탐색 실험이다. 정답 문헌 집합을 평가기에만 전달했다. 근거 문헌 집합 일치는 자연어 답변의 의미 정확도가 아니다.

| 방식 | 문항 | 정확 문헌 집합 | 필요 문헌 모두 회수 | 무효·오류 | 중앙값(초) |
| --- | ---: | ---: | ---: | ---: | ---: |
| single | 8 | 4/8 | 6/7 | 0 | 9.31 |
| decompose | 8 | 7/8 | 7/7 | 0 | 21.20 |

## 누락·실패를 읽는 방법

candidate_complete는 모델이 나눈 모든 과제에 근거 후보가 붙었다는 뜻이다. 질문 전체를 올바르게 분해했거나 선택한 문장이 그 요구를 충분히 뒷받침한다는 보장은 없다. 그래서 모델의 상태 문자열과 별도로 사람이 정한 필요 문헌 집합을 비교했다.

| 문항 | 방식 | 상태 | 기대 문헌과 일치 | 누락 표시 |
| --- | --- | --- | --- | --- |
| g1 | single | candidate_complete | False | False |
| g1 | decompose | candidate_complete | True | False |
| g2 | single | candidate_complete | True | False |
| g2 | decompose | candidate_complete | False | False |
| g3 | single | candidate_complete | False | False |
| g3 | decompose | candidate_complete | True | False |
| g4 | single | candidate_complete | True | False |
| g4 | decompose | candidate_complete | True | False |
| g5 | single | candidate_complete | False | False |
| g5 | decompose | candidate_complete | True | False |
| g6 | single | candidate_complete | True | False |
| g6 | decompose | candidate_complete | True | False |
| g7 | single | not_found | True | True |
| g7 | decompose | not_found | True | True |
| g8 | single | candidate_complete | False | False |
| g8 | decompose | partial | True | True |

GPU 전력 측정값을 묻는 요청은 현재 초록에 그 자료가 없어야 하는 음성 사례다. 원문 ID가 유효해도 관련 없는 문헌을 붙이면 평가에서는 실패로 남긴다. g8에서는 분해 방식이 방법에 대한 문헌을 찾으면서 전력 측정 과제를 누락으로 남겼다. 반면 g2에서는 “번갈아 하는 방식”을 별도 과제로 과분해해 불필요한 Adaptive-RAG 문헌을 추가했다. 원문에 있는 문구만 사용해도 과제 분해가 논리적으로 옳다는 보장은 없다.

## 지연 분석과 9번 연결

초기 부분 실행에서 복합 검색 한 건이 129.72초 걸려 전체 실행을 중단했다. 3개 완료 기록을 evidence-graph-v1-partial.json에 보존했다. 최적화 후 전체 8개를 다시 측정했으며, 초기 부분 실행을 완성된 비교표처럼 사용하지 않는다.

선택 모델에 출처 해시·URL·오프셋을 반복 전달하지 않고 짧은 출처 별칭과 텍스트만 보낸다. 원본 메타데이터는 서버에 유지한다. 동적 Pydantic 클래스가 달라도 JSON 스키마가 같으면 구조화 디코더 컴파일을 재사용한다. 선택 가능 ID가 달라지면 다른 키가 된다. 이 캐시는 이전의 동일 입력 결과 캐시나 KV 캐시와 구분한다.

추적에는 prompt_tokens·output_tokens·grammar_setup_ms·schema_cache_hit와 모델 호출 수를 남긴다. 입력 압축·토큰 예산·스키마 재사용을 함께 바꿨고 실행 부하도 달라서, 한 가지 수정의 독립적인 속도 향상률을 주장하지 않는다. 분해는 추가 모델 호출이 필요하므로 실험 옵션으로 두었다.

## 면접 설명

> 문헌 검색의 복합 요청에서 한 주제가 다른 주제의 근거를 밀어내는 문제를 다뤘습니다. 요청을 나눠 검색하되 최종 문서는 3개로 제한하고, 과제별 근거 ID를 구조화 출력으로 선택하도록 했습니다. 출처 위치뿐 아니라 추론 중 문서 버전 변경도 검사했습니다. 동시에 분해 자체의 누락과 잘못된 인용 선택을 별도로 평가했고, 추가 호출의 지연이 커 기본 검색과 실험 경로를 구분했습니다.

3번에는 복합 문헌 탐색·출처 추적·실패 분석을, 9번에는 구조화 디코더 초기화·입력 예산·단계별 지연 측정을 설명할 수 있다. 금융 안내 자료를 검수하는 내부 처리 도구로 활용하는 방향이며 고객용 금융 화면에 미검수 과학 문헌을 자동 노출하지 않는다.

설계 참고: [Question Decomposition for Retrieval-Augmented Generation](https://aclanthology.org/2025.acl-srw.32/). 논문의 전체 벤치마크를 재현한 것은 아니다.
