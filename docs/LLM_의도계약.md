# 검색 전 LLM 의도 계약

2026-11-03. 기존 서비스의 상황 채팅 → 금융 위젯 화면 흐름에서, 기능 이름을 언급했지만 실제로는 제외한 요청을 구분하기 위한 추가 단계다.

## 구조

1. 이번 사용자 발화를 최대 6개 원문 구간으로 나눈다. 구간은 실제 시작/끝 offset과 e0, e1 등 ID를 가진다. 최대 개수 이후의 뒷부분도 마지막 구간에 보존한다.
2. 기존과 같은 로컬 Qwen3-4B가 구간별로 `request / exclude / context / mixed` 중 하나를 고른다. 추가 모델 가중치를 올리지 않는다.
3. 요청마다 실제 존재하는 구간 ID만 필수 필드로 가지는 JSON 스키마를 만든다. 모델은 새 인용 문장을 쓰거나 ID를 지어내지 않는다. 각 ID에는 한 가지 판정만 있어 서로 모순된 이중 분류를 막는다.
4. 긍정 요청이 있으면 요청 구간과 중립 상황 구간을 신경망 검색에 사용한다. 제외 구간을 후보 검색에서 분리하되 최종 설계 모델에는 원문과 계약을 함께 주어 제외 조건을 반영한다. 주어가 있는 상황 구간을 남겨 “카드를 찾음 → 해제 방법” 같은 문맥이 사라지지 않게 한다.
5. 새 화면에서 상황·제외 조건만 있고 긍정 요청이 없으면 불필요한 금융 위젯을 생성하지 않고 필요한 기능을 묻는다.
6. 기존 화면에서 삭제만 요청하면 기존 위젯들 안에서 편집한다. 전체 교체 요청이면 과거 위젯을 검색 후보에 자동 보존하지 않는다.
7. 모든 화면 비우기는 LLM의 clear 판정과 실제 원문의 전체 삭제 표현이 모두 있을 때만 빈 화면 revision을 저장한다. 일반 확인 응답은 기존 화면을 보존한다.

분할 자체는 규칙 기반이며, 각 구간의 의미와 제외 범위는 LLM이 분류한다. 원문 ID와 offset은 출처의 정확성을 보장하는 장치이며 의미 판정의 정답까지 보장하지는 않는다. mixed 구간은 정보 손실을 피하려고 검색에 남기므로 부정 조건이 완벽하게 제거된다고 주장하지 않는다.

## 실행·지연 제한

- `intent_mode=off`: 기존 검색·설계 경로.
- `intent_mode=auto`: 제외·완료·유지·교체 표현이 있는 요청에서만 분류.
- `intent_mode=enforce`: 진단용 강제 분류.
- 단순 기간·금액·계산 폼 갱신은 먼저 라우팅해, enforce여도 추가 모델 호출이 없다.
- 생성은 최대 180토큰이며, 자유 형식의 장문 추론이 아니라 작은 분류 계약을 반환한다.
- 잘못된 계약은 거부하고 기존 경로를 사용한다. 모호한 LLM 판정만으로 기존 화면을 지우지 않는다.
- trace에는 구간 ID별 분류·작업 종류·지연을 기록한다. 계약 안의 원문 구간 목록을 세션 trace에 그대로 저장하지 않는다.
- React의 `understanding` 진행 문구는 실제 분류 단계에 대응한다.

추가 LLM 호출이 항상 더 좋다는 주장은 아니다. 기존의 생성 후 자기 검토는 정확도 이득이 확인되지 않아 꺼 두었다. 이 단계도 실제 비교에서 확인한 범위만 설명해야 한다.

## 평가

```bash
.venv/bin/python -m pytest tests_rag/test_intent_contract.py -q
.venv/bin/python -m rag_backend.evaluate_intent_contract
```

기존 12개 개발 회귀 문항은 이전 multi/MPS 결과와 비교한다. 별도로 `data/intent_contract_challenge_v1.json`의 8개 표현을 의도 계약 모델 실행 전에 고정하고 같은 모델·같은 장치에서 off/auto를 쌍으로 비교한다. 정답은 평가기에만 전달한다. 개발자가 작성한 작은 진단 자료이며 외부·독립 벤치마크가 아니다. 이전 실패가 기능 방향에 영향을 주었다는 사실도 명시한다.

전체 실행 결과와 실패는 `reports/intent-contract-v1.json`에 남기고, summary가 있어야 완료된 결과로 간주한다. 원문 구간 분할·이력 편집·확인 응답·revision·0-call 경로의 테스트는 실제 모델 평가와 구분한다.

## 제외 조건의 실행 계약

초기 v1 비교에서 국내여행 부정 요청 s08은 해결했지만, 후속 요청 s10은 "제외했다"는 설명과 달리 예금보호 위젯을 남겼다. 최초 28회 기록은 `reports/intent-contract-v1.json`에 보존했다. 따라서 의도 분류만으로 개선되었다고 결론내리지 않는다.

v2는 LLM이 exclude로 분류한 원문 구간을 기존 BGE 모델로 후보 위젯 목적에 연결한다. 원 점수 최고값 0.01 이상, 상대값 최고점의 0.5 이상인 경우만 제외 대상으로 삼는다. 별도 request 구간이 같은 위젯을 요구하면 보호한다. 이 값들은 개발 휴리스틱이며 신뢰도 확률이 아니다. 불명확한 구간은 강제 삭제로 바꾸지 않는다.

확인된 제외 type은 단순 설명문이 아니라 **생성 스키마의 후보와 이번 요청의 유효 registry**에서 제거한다. 뒤에서 모델이 다시 선택하거나 재검토가 되살릴 수 없게 한다. 기존 위젯 삭제만 명확히 연결되면 서버가 해당 위젯을 제거하는 patch를 적용해 추가 화면 설계 호출을 줄인다.

프론트는 실제로 남아 있는 widget ID의 입력값만 보존한다. 삭제·비운 위젯의 금융 입력 초안은 제거해 나중에 위젯을 다시 넣었을 때 예전 값이 뜻하지 않게 재등장하지 않게 한다. API 확인 응답에서는 기존 화면과 입력값을 보존한다.

LLM의 구간 판정이나 검색 모델의 주제 연결 자체가 틀릴 가능성은 남는다. 특히 부분 조건 제외를 위젯 전체 제외로 잘못 해석하지 않도록 긍정 요청 보호 검사를 추가했지만, 임의 표현의 완전한 논리 이해를 보장하지 않는다.

## 동일 위젯 반복 선택 정규화

제외 type을 막은 v2에서는 s10의 LLM 출력이 같은 위젯을 반복해 compiler의 중복 검사에 걸렸다. 프롬프트·출력 스키마는 그대로 두고, **모델 출력 어댑터**에서 동일 type 반복만 하나로 정규화하는 단계를 추가했다. 먼저 나온 순서를 유지하고 우선순위는 더 앞선 값을 사용한다. 다른 위젯을 합치거나 모델이 빠뜨린 위젯을 만들어 넣지 않는다.

현재 UI 계약은 type이 안정적인 widget ID다. 같은 type의 독립된 여러 인스턴스를 다루는 다중 시나리오 기능과는 다르다. compiler 자체의 중복 거부·상충 액션·의존관계·화면 크기 검사는 그대로 남긴다. 정규화한 type은 trace에 기록한다.

v3는 정상적으로 유일한 type을 출력했던 v2의 성공 기록을 보존하고, 실패한 s10을 실제 모델로 재시험한다. 새로 전체 20개를 모두 추론한 실행이라고 표현하지 않는다. `reports/intent-contract-v3.json`은 원래 실패·v2 파일 해시·재시험·계산/화면 비우기 검사를 함께 보존한다.

## 최종 통합 확인

[최종 집계](../reports/intent-contract-results.md)와 [검증 메타데이터](../reports/intent-contract-verification.json)에 기록했다. 국내여행의 부정 요청에서 새 금융 위젯을 만들지 않고, 기존 화면의 예금보호를 제거하면서 비용 비교를 유지하고 상환표를 추가하는 실제 React→Spring→로컬 모델 경로를 확인했다. 정확한 전체 화면 비우기는 LLM 해석 없이 source 문법으로 라우팅한다. "다시"나 "모두 지우고 새 업무 추가"를 전체 비우기로 오인하지 않는 테스트를 포함했다.
