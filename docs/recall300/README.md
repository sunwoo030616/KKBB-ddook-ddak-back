Macro Recall@K = 질문별 `|TopK ∩ gold| / |gold|`의 평균이다. 복수 정답 질문은 두 업무 모두 요청한 경우이며, 서로 대체 가능한 메뉴 후보 목록과는 다르다. 오류는 분모에 남기고 0점 처리한다. 질문당 하나만 맞아도 성공하는 hit rate와 구분한다.

## 라벨·중복·누수 한계

- 이전 작업공간의 300개 합성 질문 중 270개 단일 질문을 유지하고 마지막 30개는 앞의 30개 업무와 결합했다. 총 300개, 단일 정답 270개·복수 정답 30개다. 두 의도를 명시적으로 이어 붙인 질문으로 자연스러운 고객 복합 의도의 대표 표본은 아니다.
- 이전 300개 결과가 존재하는 상태에서 재사용했으므로 새 독립 테스트나 블라인드 평가가 아니다. 기존 99.67%/100%/100% 결과와 구성도 다르므로 개선·하락으로 비교하지 않는다.
- 메뉴 설명을 보고 작성한 합성 라벨이며 독립 전문가 검수·평가자 일치도 측정은 없다. 유효한 대체 정답이 빠질 수 있다. 정답 메뉴명을 포함한 문항은 51개다. 카탈로그 기반 작성 편향과 쉬운 질문으로 성능이 높아질 수 있다.
- 정규화 완전 중복 0개, 문자 유사도 0.9 이상 중복 후보 0쌍. 의미 중복 부재를 보장하지 않는다. 기존 개발 20문항과 완전 일치 질문·정답 ID 중복 0개. 모델 사전학습 데이터 누수는 확인할 수 없다.
- 입력·모델·카탈로그 해시를 사전 고정했고 결과를 보고 정답·K·카탈로그를 수정하지 않았다. 분류·설명은 자동화 수준의 감사이며 독립 라벨 검수는 아니다.
- 운영 K=40 유지. 복수 정답 30문항 중 Top-40에 모든 정답이 포함된 경우는 28개다. 현재 JEV는 한 메뉴를 선택하므로 이 결과만으로 복수 업무 처리 성공을 주장할 수 없다.

## 실행 설정과 재현

- 실행: `2026-11-15T06:13:30.365457+00:00` → `2026-11-15T06:13:31.739689+00:00`
- Python 3.9.6, macOS-26.5.2-arm64-arm-64bit
- E5: `intfloat/multilingual-e5-small`, revision `614241f622f53c4eeff9890bdc4f31cfecc418b3`; 기존 ONNX CPU 런타임과 manifest 체크섬 검증 사용.
- `query: ` / `passage: ` 접두어, 256 토큰, mask 평균 pooling, L2 정규화, cosine 내적, stable 정렬. 기존 585×384 캐시 사용. 실행 중 서버 코드 변경 없음.
- 운영 서비스는 민감정보 마스킹 후 E5 Top-40 → JEV 1회 → 후보 내 메뉴 검증. 이 평가는 E5 HTTP 엔드포인트만 사용하며 백엔드 마스킹·JEV·최종 UI는 평가하지 않는다.
- HTTP 시간은 로컬 왕복이며 모델 시작 시간은 제외된다. 처리량·운영 지연 보장은 아니다.

```sh
python3 -m venv .semantic-runtime/venv
.semantic-runtime/venv/bin/pip install -r scripts/semantic/requirements.txt
# 기존 scripts/semantic 모델 설치 안내에 따라 manifest와 일치하는 모델 준비
.semantic-runtime/venv/bin/python scripts/semantic/server.py --model-dir /path/to/model --catalog src/main/resources/kb_starbanking_menu_structure_cleaned.json --port 18093
# 별도 터미널; 완료 결과 덮어쓰기는 거부함
python3 scripts/semantic/recall300/evaluate.py --output /tmp/new-recall300-results.json
python3 -m unittest discover -s scripts/semantic/recall300 -v
python3 scripts/semantic/recall300/verify.py
```

`results.json`에 문항별 Top-100·정답 순위·시간·집계·감사 결과를 보관한다. `run.log`와 `tests.log`는 실제 실행 로그다. 생성 결과는 `freeze.json` 입력 해시와 함께 검토한다.
